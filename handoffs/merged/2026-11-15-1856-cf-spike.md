## What changed
- **ADR 0002 written** (Accepted, subject to Step 1 gates). Decisions: static export (not vinext); one Worker confirmed; **Queues on Free with D1 as source of truth and a 1-minute cron sweep as safety net** (`waitUntil` works and stays the fallback); **PBKDF2-SHA256 at 100,000 iterations** (platform max), stored per hash so it can be lowered, with a long generated admin password and login rate limiting.
- **Deployed measurement done** on the user's Workers Free account (confirmed Free: Cloudflare rejected `limits.cpu_ms`). Key results: static assets never invoke the Worker; webhook 4–8 ms CPU; queue consumer median 3 ms; PBKDF2 10k/25k/50k/100k = ~3/5/10/17 ms; the runtime **rejects PBKDF2 above 100,000** (local workerd does not); cron works (first fire ~15 min after first deploy) and recovered an orphaned QUEUED row.
- **Important finding:** Free-plan CPU enforcement is far looser than the documented 10 ms (100k-iteration PBKDF2 at 14–22 ms and a 245 ms request both returned ok, no 1102). The ADR treats that as leniency, not a contract.
- **vinext check**: 90% compatible (turbopack rules ignored, cacheComponents experimental), run on a copy.
- Static export needed `cacheComponents` and `partialPrefetching` gated on `NEXT_OUTPUT` (as ruled). Plain `pnpm build` is unchanged and passes.
- Fixed the previous worker's failing tests (Miniflare 5 beta had a different options shape → pinned stable `miniflare@4.20260730.0`; `routerConfig` for `run_worker_first`; Workers reject `redirect: "error"`; local workerd has no PBKDF2 cap).
- Not tested, listed in the ADR as Step 1 gates: Queue behaviour when the 10,000 ops/day quota is exhausted; whether queue consumer invocations count toward 100,000 requests/day; whether a D1 `batch` counts as one of the 50 queries; atomic-batch rollback on a deployed D1; D1 rows-written per comment (estimated, not measured).
