## What changed
- **`src/db/schema.ts`**: the six tables (`instagram_accounts`, `automations`, `webhook_events`, `deliveries`, `operational_events`, `app_settings`). `jobs` is gone. IDs are text with a `crypto.randomUUID()` default, timestamps are epoch-ms integers, enums are text plus a named `CHECK`, and `payload` is JSON text. Exports the status lists (`DELIVERY_STATUSES`, `PENDING_DELIVERY_STATUSES`, `RATE_COUNTED_DELIVERY_STATUSES`, …), row and insert types, and `oneOf()`, which inlines the values so a query can match a partial index.
  - New columns on `deliveries`: `next_attempt_at` (replaces `jobs.run_after`), `claimed_at` (replaces the job lease), `skip_reason`. Extra CHECKs: a pending row must have `next_attempt_at`, and a `SENDING` row must have `claimed_at`.
  - `app_settings.worker_heartbeat_at` is renamed `last_sweep_at`, because there is no always-on worker.
  - `operational_events_related_delivery_idx` on `related_delivery_id` (review change 2): without it, the `ON DELETE SET NULL` FK scans the table on every delivery delete.
- **Migrations**:
  - `migrations/0000_init.sql` is exactly what `pnpm db:generate --name init` produced; drizzle-kit handled every CHECK and partial index, so nothing was hand-edited.
  - `0001_seed_app_settings.sql` is a `--custom` migration that inserts the single `app_settings` row (the archive test expected a seeded row). Its `updated_at` is `CAST(strftime('%s', 'now') AS INTEGER) * 1000` (whole seconds), not `unixepoch('subsec')`, because deployed D1's SQLite version isn't confirmed (review change 3).
  - `0002_operational_events_related_delivery_idx.sql` is generated and adds the index below (review change 2). `0000` was not edited.
  - All three apply with `pnpm db:migrate:local --persist-to <scratchpad>`, and the seeded row and the new index read back.
- **`src/db/deliveries.ts`**:
  - `recordEventStatements(db, input)` returns the batch statements for one event and its delivery. `recordEvents(db, inputs[])` runs any number of them in one `db.batch` and says, per comment, whether the event was new and which delivery it created.
    - A Meta redelivery is a no-op: `ON CONFLICT DO NOTHING` on `event_key` and on `(account, comment)`.
    - **Once-per-user takes no read**: a QUEUED delivery whose automation has the setting on is inserted with the slot flag and a target-less `DO NOTHING`. A second insert, `SKIPPED` with `skip_reason='once_per_user'` and targeted on `(account, comment)`, lands only when the first was dropped because the slot was taken. All of this is in the same batch.
  - `claimStatement` / `claimDelivery`: the ruled conditional `UPDATE … RETURNING`, from `QUEUED`/`RETRYABLE_FAILED` to `SENDING`.
    - It counts `SENDING`/`SENT`/`DELIVERY_UNKNOWN` claims in the last hour **and the last minute**: limits are `{ perHour, burstPerMinute }`, the same pair `decideSend` takes.
    - When it changes no row, a follow-up read returns either `unavailable` (with the current status, or `null` if the row is missing) or `rate_limited` with `retryAt`, computed by the domain's `decideSend`.
  - `finishDelivery` moves `SENDING` **or `DELIVERY_UNKNOWN`** to `SENT` with the message ID (review change 1), so a sender that outlived the 60 s quarantine still records its success. `failDelivery` acts only from `SENDING`, so nothing moves `DELIVERY_UNKNOWN` to `QUEUED`/`RETRYABLE_FAILED`. `RETRYABLE_FAILED` requires `nextAttemptAt` (enforced by the types).
  - `quarantineStatement` / `quarantineStaleSending`: up to `limit` (default 25) `SENDING` rows older than `olderThanMs` (default 60 s) become `DELIVERY_UNKNOWN`, oldest first.
  - `pendingDeliveries`: due `QUEUED`/`RETRYABLE_FAILED` rows, earliest `next_attempt_at` first, up to `limit`.
- **`src/db/test-d1.ts`**: starts Miniflare with one D1, applies `migrations/*.sql` in order, and returns `{ d1, db, dispose }`. It also has fake-data fixtures (`insertAccount`, `insertAutomation`, `fakeId`, `failureOf`). The compatibility date is read from `wrangler.jsonc`.
- **Tests**: `schema.worker.test.ts` has 12 tests and `deliveries.worker.test.ts` has 20. They cover every item in the brief: duplicate comment is a no-op; once-per-user blocks only a counting delivery, including two concurrent batches; one active automation per media; the status `CHECK`; a concurrent claim has exactly one winner; the hour limit refuses a claim, and the claim succeeds once the oldest ages out; the burst limit; RETRYABLE_FAILED rows and other accounts don't count; finish and fail refuse rows that are queued or already sent; stale `SENDING` becomes `DELIVERY_UNKNOWN` and is then never listed or claimed, `failDelivery` on it is refused, and a late `finishDelivery` records `SENT` with the message ID (this replaces the old "late finish is refused" assertion); batch rollback. Three query-plan tests also check that the sweep, quarantine and claim count use their indexes, not table scans.
- **`src/db/README.md`**: the state machine (one line per transition, with the `DELIVERY_UNKNOWN → SENT` line), indexes kept, added and dropped (with reasons, including the new operational-events index), and the gate-2 rows-written table. Per-comment figures are unchanged: the delivery functions write no operational events. An operational event costs 4 rows locally (measured, with or without a related delivery).

## Notes for Jarvis
- **Shared file:** `src/db/schema.ts` was rewritten as briefed. `client.ts` was not touched.
- **tsconfig quirk (I did not change it):** root `tsconfig.json` type-checks every `src/db/*.ts` except `client.ts`, without Workers types. So `deliveries.ts` and `test-d1.ts` don't import `./client`: `Db` is spelled out as `DrizzleD1Database<typeof schema>` in `deliveries.ts`, and `test-d1.ts` calls `drizzle()` itself. A cleaner fix is to exclude `src/db` (or every worker-side directory) from the root tsconfig, the way `src/worker` already is. Suggest it for whoever next touches the tsconfigs.
- **Decisions made inside the rulings** (each is easy to undo):
  1. The claim's rate subquery is correlated to the claimed row's own `instagram_account_id`, not passed in as `account_id=?`, so a caller can't pass the wrong account.
  2. A per-minute burst subquery sits next to the hour one, because `decideSend` enforces both and 2b would otherwise lose the burst limit.
  3. The claim does not check `next_attempt_at`, so an early duplicate queue message can claim a retry before its backoff ends. It still can't cause a duplicate send.
  4. The once-per-user fallback uses `SKIPPED` + `skip_reason`.
- **Not done, for later phases:**
  - Releasing the once-per-user slot on `PERMANENT_FAILED`/`EXPIRED`: the archive said a failed delivery "can" release it; that's a product call.
  - Writing `EXPIRED`.
  - Checking `sends_paused` or the connection status before a claim (2b).
- Applying the migrations to a real D1 is yours: `wrangler d1 migrations apply fewchat-db --remote` with the deploy config.
