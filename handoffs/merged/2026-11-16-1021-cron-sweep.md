## What the user asked
Make the deployed Worker deliver: `queue()` hands batches to `handleDeliveryBatch` with real dependencies built from `env`, and `scheduled()` runs a bounded per-minute sweep that quarantines stale `SENDING` rows and processes a few overdue pending deliveries inline. Prove both through the real Worker in Miniflare against a fake Meta origin.

## What changed
- `src/worker/deps.ts`: `deliveryDependencies(env, { fetch })` is the one factory, built from `parseEnv(env)` as ruled (`getDb`, `createMetaClient` on `https://graph.instagram.com` with `META_GRAPH_API_VERSION`, limits 600/h and 30/min, `Date.now`, `Math.random`). Its default `fetch` is `(request) => globalThis.fetch(request)`, not the bare `globalThis.fetch` the brief sketched: the Meta client calls `config.fetch(request)` as a method, and workerd throws "Illegal invocation" for that on the bare function.
- `src/worker/sweep.ts`: `runSweep(deps, { now })` in the ruled order: quarantine stale `SENDING` (60 s, limit 25); pending rows due at least 60 s ago (`SWEEP_OVERDUE_MS`), oldest first, `SWEEP_BATCH_LIMIT = 5` (comment points at gate 3); `processDelivery` on each, sequentially and inline; a throwing row is counted by fixed class (`BeforeClaimError` / `ClaimOrProcessingError`, never the message) and the sweep goes on; then one `last_sweep_at` write and one JSON log line of counts. It returns the summary.
- `src/db/settings.ts`: `readSettings(db)` and `touchLastSweep(db, now)`. `readSettings` is used only by tests so far; the Health page will use it.
- `src/worker/index.ts`: `queue(batch, env)` → `handleDeliveryBatch(batch, deliveryDependencies(env))`; `scheduled(_, env)` → `runSweep(deps, { now: deps.now() })`. A `parseEnv` failure makes `queue()` call `retry()` on every message and `scheduled()` return, each after one fixed log line with no detail. The sweep uses the clock at invocation, not `controller.scheduledTime`, so a late cron start does not make the 60 s margin look longer.
- `src/worker/harness.ts`: every outbound `fetch` from the Worker now goes through a Miniflare `outboundService` to a fake origin, exposed as `meta.requests` (url, method, authorization, body) and `meta.respond` (scriptable, defaults to an accepted send). It is test-only: the Worker still calls `graph.instagram.com`, and there is no env var or production code path for it. New `env` option overrides fake bindings (used for the bad-config test).
- `src/worker/README.md`: the file list, and a "Queue and sweep" section with the order, limits and why.
- Tests, all through the real Worker unless noted (`sweep.worker.test.ts`, `index.worker.test.ts`):
  - a signed webhook → its queue message through `queue()` → row `SENT`, one Meta request to `/v24.0/<ig user id>/messages`;
  - `scheduled()`: a row due 90 s ago → `SENT`, one due 10 s ago untouched;
  - a stale `SENDING` row → `DELIVERY_UNKNOWN` (`stale_sending`), no request;
  - 7 overdue rows → the 5 oldest `SENT` on tick 1, all 7 after tick 2;
  - paused → no request, rows stay `QUEUED`; unpause → next tick sends;
  - one row whose claim throws (a D1 trigger) → it stays `QUEUED`, the other two are `SENT`;
  - `last_sweep_at` is null, then set, then advances;
  - bad config (short `TOKEN_ENCRYPTION_KEY`): `queue()` retries both messages with no request and no row change; `scheduled()` returns ok and touches nothing;
  - `index.worker.test.ts`: the old "queue acks" and "scheduled logs" tests now cover an unknown-delivery and a malformed message (both acked, no Meta request) and a sweep stamping `last_sweep_at`;
  - direct `runSweep` (not through the Worker, since Worker logs can't be captured): the log line is exactly the counts, with no delivery IDs and none of a thrown error's message.
