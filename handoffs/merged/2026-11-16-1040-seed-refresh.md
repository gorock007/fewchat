## What the user asked
`pnpm seed` puts the real Instagram account and one automation into local or remote D1 without the dashboard or OAuth, so the Step 3 live Meta test can run. The cron sweep refreshes a connected account's long-lived token before it expires. The user's answers to my first-handoff questions are applied: one `--keyword` only, `--once-per-user` present → true / absent → false (printed), optional `--account` and `--name`, null `token_refreshed_at` counts as old enough.

## What changed
- **Schema**: `instagram_accounts.token_refreshed_at` and `token_refresh_attempted_at` (nullable, epoch ms). Migration `0003_sloppy_mephistopheles.sql`, generated with `pnpm db:generate`, not applied anywhere real.
- **Token refresh** (`src/worker/refresh.ts`, called from `runSweep` after quarantine and before pending rows):
  - Due = `connected`, token present, under 7 days left, `token_refreshed_at` null or at least 24 h old, `token_refresh_attempted_at` null or at least 1 h old. At most one account per tick, soonest expiry first.
  - It stamps the attempt first, conditional on the ciphertext read. Success stores a new envelope, `token_expires_at` from `expires_in` and `token_refreshed_at` = now, all conditional on the old ciphertext.
  - `token_invalid` and `permission_denied` call `markNeedsReconnect`. Anything else leaves the account for the retry an hour later.
  - The sweep summary and its one log line gain `refreshed` and `refresh_failed` (0 or 1). A thrown error counts as `errors.RefreshError` and the sends go on. The token and Meta's failure text are never logged.
- **Seed CLI** (`pnpm seed`, no new dependency):
  - `scripts/run-seed.mjs` bundles `scripts/seed.ts` with the existing `esbuild` into a temp dir and runs it. Node's type stripping can't resolve `src/`'s extensionless imports.
  - `account`: the token comes from stdin only. It reads `TOKEN_ENCRYPTION_KEY` and `META_GRAPH_API_VERSION` from the environment or `.dev.vars`. It calls `getAccount` then `subscribeAccount`; a subscription failure is recorded as `failed` and the seed carries on. It encrypts with the local row id and upserts on `instagram_user_id`. Re-seeding keeps the existing row id, replaces the token and sets `connected`; it looks the id up with a `wrangler d1 execute --json` read first, because the token's encryption is bound to the id.
  - `automation`: `--media`, one `--keyword` or `--any`, `--match`, `--url`, `--message`, `--once-per-user`, `--account`, `--name`. It validates with `validateResourceUrl` and `validateTemplate`, deactivates any other active automation on that media first, then inserts. A repeated `--keyword` is an error that says so. With no `--account` it attaches to the only account; with none or several it fails with a hint to seed an account first or pass `--account`.
  - Writes go through `wrangler d1 execute DB --local|--remote [--config f] --file <tmp.sql>`, with the file in a fresh temp dir that is deleted afterwards. It prints only the username, IG user id and subscription result, or the automation id and what it was set to. `--help` lists the Step 3 flow.
  - Plaintext token handling: used only for the Meta calls and the encryption. It is never in argv, the SQL file, stdout or an error message. Unexpected errors print only their class name.
- **README** "Seeding for the live test" subsection (local and `--remote --config wrangler.deploy.jsonc`), plus the `src/worker` and `src/db` READMEs.

## Notes for Jarvis
- **Apply migration `0003` yourself** (`pnpm db:migrate:local` locally; the remote D1 before the cron runs the new sweep, or the due-account select fails with a missing column and counts `RefreshError`).
- **Test placement:** `vitest.config.ts` only includes `src/**`, and it was off my list, so the CLI's tests live in `src/db/accounts-write.worker.test.ts` (clearly labelled). If you'd rather have `scripts/seed.test.ts`, add `scripts/**/*.test.ts` to the config's `include` and move them.
- **Typing gap:** `DeliveryDependencies.meta` (in `src/delivery/process.ts`, off my list) only names `sendPrivateReply`. `SweepDependencies` therefore makes `refreshToken` optional and throws a counted `RefreshError` if a token is due and the client lacks it; the real client has it. Widening that type, or `deliveryDependencies`' return type in `src/worker/deps.ts`, would let it be required.
- **Gap-fills outside the brief:** a token that fails to decrypt during refresh goes to `needs_reconnect` (as in the send path). A token already expired (past `token_expires_at`) is still picked up, so Meta's `token_invalid` moves it to `needs_reconnect` instead of leaving it `connected`.
- **Limits to know:**
  - `wrangler d1 execute --file` is not a transaction. The automation SQL runs "deactivate others, then insert", so a failed insert after validation would leave that media with no active automation.
  - The Meta client sends `access_token` in the query string on `subscribed_apps` and `refresh_access_token`. That is its existing design, not mine.
  - The seed's `--expires-in` defaults to 60 days from now, which is a guess, since `/me` doesn't report expiry. The first refresh corrects it from Meta's real `expires_in`.
